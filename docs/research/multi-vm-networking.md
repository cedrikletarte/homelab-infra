# Networking and routing across Docker VMs on Proxmox

Research date: 2026-11-26. Status: findings only, no decision.

Question (ticket hl-e2c.24): with Docker services spread across the eight Role VMs of
ADR 0001, how are they connected to each other, to the LAN and to the Internet? Covered:
Traefik routing to services in other VMs and its effect on CrowdSec; host/VM/LAN networking
(Linux bridge, VLANs, Proxmox SDN, Proxmox firewall) behind an unmanaged 1 Gbps switch and a
Bell Home Hub 4000; the VPN Server (current WireGuard vs Tailscale/Headscale); local DNS; a VM
reaching the Shared Database in another VM; one host ZFS dataset shared into two VMs
(virtiofs vs NFS) with *arr hardlinks intact, including Proxmox VE 9 virtiofs limits.

Principles applied: reliability and low upkeep first; a dedicated tool beats a home-made
script; every piece of complexity must pay for itself.

Every claim carries a numbered source (list at the end). Text marked "inference" is
reasoning on top of the sources, not a quote. Addresses, domains and paths are placeholders
(`<lan-subnet>`, `<platform-vm-ip>`, `example.com`, `<pool>/media`).

## TL;DR

- **Layer 2 is simple and mostly fixed by the hardware.** The Hub 4000 exposes little
  configuration (community reports: no way to stop its DNS relay, DHCP toggle reverting)
  [B1][B2], and the switch is unmanaged, so VLANs cannot reach the router. The default
  Proxmox bridged model (every VM on `vmbr0`, as if plugged into the LAN switch) [P4] is the
  baseline. The one cheap refinement is a second, host-only bridge with no physical port for
  VM-to-VM back-end traffic (database, proxy to backend, NFS). VLANs, SDN zones and a router
  VM add pieces without solving a problem this LAN has.
- **The Proxmox firewall is the natural place to filter between VMs.** It runs on the host,
  filters each VM NIC, and is not bypassed by Docker inside the guest, while Docker-published
  ports bypass guest ufw rules [P5][D1]. It is off by default and needs enabling per cluster
  and per NIC [P5]. The nftables backend left tech preview in 9.3 but stays opt-in [P2].
- **Traefik loses Docker-label discovery across VMs** (one `providers.docker` reads one
  daemon [T1]). Options: one central Traefik with file-provider rules (today's
  `nextcloud.yml` pattern, generated by the planned automation); one central Traefik fed by
  **traefik-kop** + Redis (labels stay, one more component, one active maintainer) [K1]; or
  a Traefik per VM behind the central one or behind cloudflared. The central options keep
  CrowdSec exactly as today. The per-VM options need a CrowdSec log processor per VM, the
  LAPI and AppSec reachable over the network, and they tie every VM's traffic to the
  Platform VM anyway, because the bouncer blocks when AppSec is unreachable (default
  `crowdsecAppsecUnreachableBlock: true`, as set in this repo) [C2].
- **VPN:** the current WireGuard container keeps working in the Platform VM with the same
  port forward. Tailscale needs no port forward and gives split DNS, but depends on a SaaS
  control plane (existing connections survive its outages) [S2][S3]. Headscale removes the SaaS
  but needs its own public HTTPS endpoint that **cannot sit behind the Cloudflare tunnel**
  [H3]. Where the VPN runs matters more than which one: in the Platform VM, a Platform VM
  outage also removes remote access to the Proxmox host.
- **Local DNS:** the Hub relays DNS and gives little control [B1][B2]. Options range from
  "no local DNS" (LAN traffic goes through Cloudflare, with a 100 MB upload cap on the Free
  plan [CF3]) to a resolver (AdGuard Home 1.0, Pi-hole 6, Technitium 15) in the Platform VM,
  to public Cloudflare records that point at private addresses.
- **Shared Database across VMs:** publish 5432 on the database VM, ideally on the host-only
  bridge, and restrict it with the Proxmox firewall and `pg_hba.conf`. The official image
  accepts password logins from any address by default [D3][D4]. Docker Swarm overlay
  networks would keep the `postgres` hostname but require a swarm over eight VMs [D2].
- **Media sharing:** hardlinks need downloads and library on **one** filesystem, which on
  ZFS means one dataset, not child datasets [TR1]. Both virtiofs and NFS pass `link()`
  through within one dataset. Proxmox 9 virtiofs (since 8.4) [P3] blocks only stateful
  operations: live migration, snapshots **with RAM**, hibernation. Disk-only snapshots
  stay allowed (qemu-server code) [P6]. It also forbids memory hotplug, hangs the mount if
  virtiofsd dies, and has **no read-only flag** in the Proxmox config [P1][P6]. NFS keeps every
  VM feature but adds a host NFS server, network exports and mount-ordering care. With
  either one, Plex in the GPU VM cannot rely on inotify for changes made by the Media VM [X1].

## 1. Today's setup (read from the repo)

- `infrastructure/network/docker-compose.yml`: cloudflare-ddns (updates the VPN hostname,
  not proxied), cloudflared (token tunnel, on the `proxy` network), WireGuard
  (linuxserver image, `51820/udp` published, one peer, full tunnel, `PEERDNS=auto`), Traefik
  v3.7 (80/443 published, dashboard bound to the LAN IP, Docker provider plus file provider
  on `traefik/dynamic`, ACME DNS-01 through Cloudflare), CrowdSec 1.8.2 (Traefik log,
  `auth.log`, AppSec on `0.0.0.0:7422`).
- The `proxy` (`172.19.0.0/16`) and `default` (`172.18.0.0/16`) subnets are pinned because
  other places trust them: Traefik `forwardedHeaders.trustedIPs`, the bouncer's
  `forwardedHeadersTrustedIPs`, the `login-ratelimit` `excludedIPs`, Vaultwarden and
  Nextcloud trusted proxies, and host ufw rules.
- The bouncer plugin reaches `crowdsec:7422` for AppSec, with `crowdsecAppsecFailureBlock`
  and `crowdsecAppsecUnreachableBlock` both `true`. Mode is the default (`live`).
- Routing is mostly Docker labels with `traefik.docker.network=proxy`. The one file-provider
  route, `nextcloud.yml`, already points at a container by name (`nextcloud-aio-apache:11000`).
- The Shared Database (`stacks/database`) listens on the `db_network` Docker network and on
  `127.0.0.1:5432` only. Its consumers are n8n (`stacks/management`) and Grafana
  (`stacks/monitoring`).
- Plex runs with `network_mode: host`. qBittorrent shares Gluetun's network namespace. The
  *arr and Plex mount the same `${MEDIA_PATH}:/data`.
- There is no local DNS server in the repo.

Everything above that relies on a Docker network name or a Docker subnet (`crowdsec:7422`,
`postgres:5432`, `nextcloud-aio-apache`, `172.19.0.0/16` as "the proxy") stops working as
soon as the two ends live in different VMs: Docker's embedded DNS and bridge networks are
local to one daemon (inference from how Docker bridge networks work; overlays are the
exception, section 7).

## 2. Host, VMs and LAN (layer 2/3)

### 2.1 Constraints

- **Router:** Bell Home Hub 4000. Community reports (not Bell documentation): DNS servers set
  in the Hub are not handed to DHCP clients; the Hub hands out itself and acts as a **DNS
  relay**; turning its DHCP server off failed (the slider reverted); and "customization of
  the HH4000 is not granular" [B1]. A Bell moderator confirms the relay behaviour and that
  DHCP is configured under Advanced tools > DHCP [B2]. The reports date from 2021 to 2022, so
  current firmware must be checked on the real device.
- **Switch:** unmanaged 1 Gbps, so no VLAN configuration, no port isolation and no LACP
  (inference: these need a managed switch).
- **NICs on the board:** Intel I211 (1G) and Realtek RTL8125 (2.5G) (from the host-layer
  research). With a 1G switch, the second NIC adds nothing for LAN throughput.
- **VM-to-VM traffic on one bridge never leaves the host.** It goes through the in-kernel
  bridge between virtio NICs, so it is not capped by the 1G switch (inference from the
  bridged model [P4]). VirtIO is the NIC model Proxmox recommends for performance [P1].

### 2.2 Options

**A. Single LAN bridge (Proxmox default).** Every VM gets one virtio NIC on `vmbr0` and an
address on the LAN, either static in the guest or a DHCP reservation on the Hub. Proxmox
describes this as "similar in effect to having the Guest network card directly connected to
a new switch on your LAN" and calls it the right model for a server in a private LAN behind
an external gateway [P4].
- For: zero extra configuration; every VM can be reached from the LAN and the VPN; Plex
  discovery and the Samba LXC just work.
- Against: every VM and every published port is on the LAN unless filtered. Back-end
  ports (Postgres, AppSec, LAPI, exporters) need firewall rules to stay off the LAN.

**B. LAN bridge + host-only bridge.** A second bridge (`vmbr1`) with no physical port. VMs
that serve back-end traffic get a second NIC on it, with static addresses from a private
range that the LAN does not use. Proxmox SDN's Simple zone builds the same thing ("not
linked to a physical interface, and VM traffic is only local on each node"), optionally
with SNAT, DHCP and port isolation [P7]. DHCP in SDN (IPAM) is still a tech preview [P7].
- For: Postgres, the Traefik-to-backend hop, NFS, CrowdSec LAPI/AppSec and metrics bind to
  addresses the LAN cannot route to (defence in depth on top of the firewall). The internal
  address plan does not depend on the Hub.
- Against: two NICs and two addresses per VM to manage; one more thing to get right in the
  VM automation. A plain `vmbr1` in `/etc/network/interfaces` is simpler than an SDN zone
  for a single node (inference: SDN's value is multi-node VNets and IPAM [P7]).

**C. VLANs on a VLAN-aware bridge.** Proxmox supports VLAN tags per VM NIC on a VLAN-aware
bridge, or through an SDN VLAN zone [P4][P7]. With an unmanaged switch and a Hub that
offers no VLAN settings [B1], tagged VLANs could only live inside the host, and routing
between them would need a router/firewall VM (inference). That doubles the moving parts of
option B for the same isolation, which the Proxmox firewall already provides per NIC.

**D. NAT/routed guests behind the host.** Proxmox documents masquerading for hosts with a
single public IP at a hosting provider [P4]. On a home LAN it hides the VMs behind the
host's address and needs port forwards on the host for every service reachable from the
LAN (inference). It fits a hosting provider, not this LAN.

### 2.3 Filtering between VMs: the Proxmox firewall

- Three zones: host (datacenter/host rules), VM (per guest, in and out only) and VNet
  (forward rules, SDN only) [P5]. The iptables service "provides full isolation between
  virtual machines" [P5].
- Disabled by default. It needs `enable: 1` at datacenter level **and** the firewall flag on
  each virtual NIC. When enabled, the host blocks everything except management from the
  local network. Keep an SSH session open while enabling it [P5].
- Building blocks: security groups (for example one per role), IP sets (`+name`), aliases,
  and the `management` IP set for GUI/SSH access [P5].
- Backend choice: the iptables `pve-firewall` is the default. The nftables `proxmox-firewall`
  left tech preview in 9.3 and "remains opt-in" [P2]. It needs no `fwbrX` bridges for Linux
  bridges, drops instead of rejecting guest traffic, and is the only backend that applies
  forward (VNet) rules. Switching requires restarting the guests [P5]. PVE 9.3 also validates
  firewall rules more strictly (known issue in the release notes) [P2].
- Why it matters with Docker: Docker routes published-port traffic in the `nat` table before
  ufw's chains see it, so ufw inside a VM does not filter published ports [D1]. A rule on the
  Proxmox side filters at the VM's NIC, below anything Docker does in the guest (inference
  from where each firewall sits).
- Also available, with no firewall at all: bind published ports to a specific address
  (as the repo already does with `${LAN_IP}`), for example the host-only bridge address.

## 3. Traefik routing to services in other VMs

Fixed constraint: a Traefik instance has a single `providers.docker` block with one
`endpoint` [T1], so it discovers containers from one Docker daemon. It can point at a remote
daemon over TCP/SSH with TLS, but that exposes a root-equivalent API across the network
(Traefik's own warning [T1]), and the container IPs it learns are not routable from another
VM unless it is told to use published ports (`useBindPortIP`) [T1].

### Option R1: one central Traefik, file provider

Traefik in the Platform VM keeps the Docker provider for the Platform VM's own containers.
Each service in another VM gets a router + service in `traefik/dynamic/*.yml` pointing at
`http://<vm-ip>:<published-port>`, exactly like today's `nextcloud.yml` (which only has to
swap a container name for an address). Traefik recommends the `directory` form and mounting
the parent directory, since bind-mounted single files lose change notifications [T2].
- Each backend publishes its port on the VM's LAN or host-only address.
- For: no new component; one place for TLS, middlewares and CrowdSec; works when a VM is
  down (the route returns 502, nothing else changes); the planned VM automation can render
  the files from an inventory (a template in a dedicated tool, not a bespoke script).
- Against: routing moves out of the stack's compose file. Adding a service touches two
  places: the stack, and the routes file plus the published port. Labels that remain in other
  VMs are dead weight.

### Option R2: one central Traefik, traefik-kop + Redis

traefik-kop runs on each VM, reads that VM's container labels and writes them to Redis.
Traefik reads Redis through its native Redis provider [K1][T4]. kop substitutes the host IP
and published port for the container address (order: `kop.<service>.bind.ip` label, then
`kop.bind.ip`, then the container network IP if `traefik.docker.network` is set,
`BIND_IP`, `BIND_INTERFACE`, auto-detected IP) [K1].
- For: labels stay in each stack's compose file, the deployment unit stays self-contained,
  and routes appear and disappear with containers.
- Against: two more components (a kop agent per VM with the Docker socket, and Redis with
  keyspace notifications enabled, which Traefik's Redis provider requires [T4]). Redis keys
  carry a TTL renewed by each agent, and each agent needs a unique `KOP_HOSTNAME`. Ports
  published on loopback only are unreachable from Traefik [K1]. Project health: last release
  v0.21.0 on 2026-10-13, 527 stars, and one maintainer with about 240 commits against
  single digits for everyone else (GitHub API, 2026-11-26) [K2]. The README states no
  Traefik version; it relies on Traefik's generic Redis provider [K1].
- Middlewares referenced from labels (`crowdsec@file`) still resolve against the central
  file provider (inference from the provider namespace model).

### Option R3: one central Traefik, HTTP provider fed by a generator

Traefik polls an HTTP endpoint (default every 5 s) that returns file-provider-format
YAML/JSON [T3]. Something has to serve that endpoint by aggregating the VMs. No maintained
off-the-shelf aggregator turned up in this research, so this amounts to writing R2 yourself
(inference). Listed for completeness.

### Option R4: a Traefik per VM, behind the central Traefik

Each VM runs its own Traefik with the Docker provider (labels unchanged). The central
Traefik holds one file-provider route per hostname, or a `HostRegexp` per VM, pointing at
that VM's Traefik.
- For: labels and per-stack routing stay local. A VM's routing works without the Platform VM
  for LAN clients who address that VM directly.
- Against: eight Traefik instances to update and configure, two hops, two places where
  forwarded headers must be trusted (the VM's Traefik must trust the central Traefik's
  address), and the central file still changes for every new hostname unless wildcards are
  used. TLS is either terminated twice, which needs certificates in every VM (a Cloudflare
  DNS token per VM), or plain HTTP on the inner hop, which is acceptable only on the host-only
  bridge (inference).

### Option R5: a Traefik per VM, directly behind cloudflared

A token-managed tunnel maps each public hostname to an origin URL, and the origin can be any
address cloudflared reaches, so hostnames can point straight at different VMs [CF1][CF2].
cloudflared replicas exist for failover, not for steering traffic [CF4].
- For: no central reverse proxy hop.
- Against: TLS, middlewares and CrowdSec are replicated per VM (section 4). Private
  Access services still need a LAN entry point. Edge configuration moves to the Cloudflare
  dashboard per hostname.

### Cross-cutting effects (all options)

- Backends in other VMs see the Platform VM's address (or the VM Traefik's) as the client.
  Everything that trusts `172.19.0.0/16` today (Nextcloud and Vaultwarden trusted proxies,
  `login-ratelimit` exclusions) must trust that address instead.
- `trustedIPs` on Traefik's entry points stays as is for cloudflared, as long as cloudflared
  sits next to the central Traefik.
- Nextcloud AIO currently joins the `proxy` network to be reached as
  `nextcloud-aio-apache:11000`. In another VM, its Apache port must be published on a VM
  address instead.

| | R1 file provider | R2 traefik-kop | R4 Traefik per VM + central | R5 Traefik per VM + tunnel |
|---|---|---|---|---|
| New components | none | Redis + 8 agents | 7 Traefik | 7 Traefik |
| Labels stay in stacks | no | yes | yes | yes |
| CrowdSec change | none | none | agents per VM + remote LAPI/AppSec | agents per VM + remote LAPI/AppSec |
| Certificates | central | central | central (+ per VM if TLS inside) | per VM |
| Dependency on a small project | no | yes | no | no |

## 4. Effect on CrowdSec

Facts: a CrowdSec deployment splits into one LAPI, log processors (agents) that can run on
other machines and register with the LAPI, and remediation components (bouncers) that query
the LAPI over HTTP. "Log processors do not share any information between them" [C1]. An
agent registers with `cscli lapi register --url ...` and is validated on the LAPI (or uses
TLS auth). Several bouncers can share one API key since 1.6.4 [C1]. In Docker, agent-only
mode uses `DISABLE_LOCAL_API=true`, `LOCAL_API_URL`, `AGENT_USERNAME` and `AGENT_PASSWORD`
[C3]. The Traefik bouncer plugin reaches `crowdsecLapiHost` (default `crowdsec:8080`) and
`crowdsecAppsecHost` (default `crowdsec:7422`). `crowdsecAppsecUnreachableBlock` (default
`true`) blocks requests when AppSec is unreachable. In `live` mode (this repo's default), any
LAPI failure blocks unless `updateMaxFailure: -1`. `stream` mode keeps a local ban list
refreshed every 60 s [C2]. Latest releases as of 2026-11-26: CrowdSec 1.8.2 (1.8.3-rc1 out), bouncer
plugin 1.8.2 (this repo pins 1.4.5) [C4].

- **R1/R2 (central Traefik):** nothing changes. CrowdSec reads the central access log, the
  bouncer and AppSec stay on the `proxy` network, and all public HTTP passes through one
  place. Gap: `auth.log` acquisition only covers the Platform VM. SSH on the other VMs is
  covered only by adding agents there (or by keeping SSH off public exposure, which is
  already the case).
- **R4/R5 (Traefik per VM):** each VM needs (a) a CrowdSec agent reading its own Traefik
  access log, registered with the central LAPI, (b) a bouncer config pointing at
  `<platform-ip>:8080` and `<platform-ip>:7422`, so LAPI and AppSec must listen on a routable
  address with firewall rules allowing only the VMs. Failure coupling: with the repo's
  settings, a Platform VM outage blocks every request in every VM (AppSec unreachable). To
  decouple, switch to `stream` mode with `updateMaxFailure: -1` and relax
  `crowdsecAppsecUnreachableBlock`, giving up WAF protection during the outage [C2]. In R4
  the inner Traefik also needs the central Traefik in its trusted IPs so the bouncer sees the
  real client.

## 5. VPN Server

### Facts

- Current: linuxserver WireGuard container, `51820/udp` published and forwarded on the Hub,
  DDNS through cloudflare-ddns, one peer, full tunnel. `PEERDNS=auto` uses the Docker host's
  DNS through the bundled CoreDNS [W1].
- **Tailscale:** a subnet router advertises LAN routes so devices without Tailscale are
  reachable; on Linux it needs IP forwarding, and it SNATs by default
  (`--snat-subnet-routes=false` to keep source IPs) [S1]. Without a direct path, traffic
  goes through peer relays, then DERP [S4]. If the coordination server is down, existing
  connections keep working and cached policy stays enforced, but no new devices, no key
  refresh, no rule changes and no revocations [S2]. The Personal plan is free: up to 6
  users, unlimited user devices, 50 tagged resources [S3]. Client 1.104.7 (2026-11-12) [C4].
- **Headscale:** an open-source control server for "a single Tailscale network (tailnet)",
  not associated with Tailscale Inc. (one maintainer is employed there) [H1]. Supports
  subnet routers, exit nodes, MagicDNS, split DNS, ACLs/grants, auto-approvers, embedded
  DERP, OIDC [H2]. Needs a publicly reachable HTTPS endpoint on 443/tcp, plus 3478/udp if the
  embedded DERP is on [H4]. "Running Headscale behind a Cloudflare Proxy or Cloudflare Tunnel
  is not supported and will not work" (the protocol upgrades a POST to
  `tailscale-control-protocol`) [H3]. v0.29.8 released 2026-11-26 [C4].

### Options

**V1. Keep the current WireGuard container in the Platform VM.** Same compose service, the
Hub's port forward retargeted to the Platform VM's address. Peers reach every VM on the LAN
bridge through the container's NAT (inference: the peer subnet must be routed or NATed to
reach the other VMs, as today). Point `PEERDNS` at the local resolver if one is added (section 6).
- For: no change, no third party, already proven.
- Against: manual peer management; a Platform VM outage also removes remote access to the
  Proxmox host and its console.

**V2. WireGuard outside the Platform VM** (on the Proxmox host, or a small dedicated guest).
- For: remote admin access survives any VM failure, which is the one case where the VPN
  matters most.
- Against: the Hypervisor Host stops being "Proxmox, ZFS and guests only" (ADR 0001), or one
  more guest to maintain. ADR 0001 allows LXC only for non-Docker services that need a host
  dataset, so a WireGuard LXC would not qualify as written.

**V3. Tailscale (SaaS control plane) with a subnet router.** In the Platform VM, on the host,
or both (two routers for failover).
- For: no port forward and no DDNS, NAT traversal, split DNS to the local resolver, easy peer
  onboarding, and policy instead of `AllowedIPs`.
- Against: depends on an external company for onboarding and key refresh [S2]; another agent
  to update; double NAT/relay paths add latency when direct paths fail [S4].

**V4. Headscale + Tailscale clients.** Same client side as V3 without the SaaS.
- Against: needs its own forwarded 443/tcp (the tunnel cannot carry it [H3]), so it must
  share 443 with Traefik on the Platform VM (Traefik routing with WebSocket upgrade) or use
  another IP/port. It is a self-hosted control plane whose outage blocks onboarding (by
  analogy with [S2]). Most upkeep of the four.

## 6. Local DNS

What it solves: LAN and VPN clients reach `service.example.com` at Traefik's LAN address
instead of going through Cloudflare. Through the tunnel, uploads are capped at 100 MB on the
Free plan [CF3] (relevant to Immich and Nextcloud on the LAN), and every LAN request depends
on the Internet link (inference). It also gives names to the eight VMs.

Distribution constraint: the Hub relays DNS and could not be made to hand out another
server, nor to disable its DHCP, in the community reports [B1][B2].

**N1. No local DNS.** Public names through Cloudflare for everything; Private Access by
`IP:port` or through the VPN. Zero upkeep; keeps the upload cap and the Internet dependency.

**N2. Public records pointing at private addresses.** For example `*.lan.example.com` as
non-proxied A records at Cloudflare to Traefik's LAN address. Certificates already come
from DNS-01. No server to run; works on the LAN and the VPN. Against: the internal address
leaks in public DNS, and some resolvers or routers drop private answers as DNS-rebinding
protection; whether the Hub does is unknown (inference, verify on the device).

**N3. A local resolver in the Platform VM** (AdGuard Home, Pi-hole or Technitium), with a
wildcard rewrite or record for the domain pointing at Traefik, and host records for the VMs.
Current releases: AdGuard Home 1.0.0 (2026-11-19, new release model where minor versions may
break compatibility) [A1], Pi-hole 6.6 (2026-11-11), Technitium 15.6.2 (2026-10-17) [C4].
Technitium has built-in clustering since v14 (configuration sync, DHCP scopes excluded)
[TN1]. Ways to deliver it to clients:
- set it as the Hub's DNS, so the Hub relays to it [B2] (per-client stats are lost, and a
  2021 report saw relayed queries fail [B1]: test it);
- disable the Hub's DHCP and serve DHCP from the resolver (reported not to stick on the
  HH4000 [B1]: test it);
- configure DNS per device (static), or only for VPN clients (`PEERDNS`, or Tailscale split
  DNS [H2][S1]).
Against: it becomes a single point of failure for name resolution on the LAN if it is the
only resolver. A second instance (another VM, or the host) or a public fallback, which
breaks local names while it is in use, is needed (inference).

**N4. Tailscale MagicDNS** for VM and device names, only for tailnet members (V3/V4).

VM-to-VM names (Postgres host, LAPI, Traefik backends) are independent of the above:
static addresses on the host-only bridge plus `extra_hosts` or `/etc/hosts` rendered by the
VM automation need no DNS server at all (inference).

## 7. A VM reaching the Shared Database in another VM

Facts: the official image adds `host all all all scram-sha-256` to `pg_hba.conf` on first
init (unless `POSTGRES_HOST_AUTH_METHOD` says otherwise) [D3], so any address that can reach
the port gets a password prompt. `pg_hba.conf` is first-match; `hostssl` matches only TLS
connections and requires `ssl = on` [D4]. Docker overlay networks need every host in a swarm
(`docker swarm init`), `--attachable` for non-swarm containers, and 2377/tcp, 7946/tcp+udp,
4789/udp between hosts. Encryption (IPsec) costs performance [D2].

**DB1. Published port on the database VM, filtered.** Publish `5432` on the VM's address
(host-only bridge if option B, otherwise LAN), allow only the consumer VMs in the Proxmox
firewall, and replace the default `host all all all` line with one per consumer address and
database. Clients use `<db-vm-address>:5432`.
- For: plain Postgres, no new component. Within the host-only bridge, TLS is optional
  (inference: traffic never leaves the host).
- Against: the `pg_hba.conf` edits are a step the image does not automate; without the
  firewall or a bind address, the port is on the LAN.

**DB2. DB1 plus TLS** (`hostssl` + `ssl = on` with a certificate), if the port is on the LAN
bridge. Adds certificate renewal.

**DB3. Docker Swarm overlay** (attachable, encrypted) so consumers keep `postgres:5432`. Keeps
names but puts a swarm control plane across the VMs for one database. That is complexity this
case does not justify (inference).

**DB4. Dedicated Database per consumer VM.** Avoids the crossing at the cost of more Postgres
instances to upgrade and back up; a change to the Shared Database policy (GLOSSARY).

**DB5. Over a tailnet** (Tailscale on each VM, Postgres bound to the tailnet address).
Encrypted, but every VM now depends on the VPN layer for database access (inference).

The same patterns apply to the other cross-VM back-end services: CrowdSec LAPI/AppSec,
Immich machine learning (GPU VM), Prometheus scrape targets.

## 8. Sharing one ZFS dataset into two VMs with hardlinks

ADR 0001: the library is mounted read-write in the Media VM, with downloads on the same
dataset, and read-only in the GPU VM (Plex).

### Hardlink rules (apply to every option)

- Hardlinks and instant moves need "all paths to be on one filesystem"; "You CAN'T hardlink
  across separate file systems, partitions, volumes or mounts" [TR1]. Each ZFS dataset is its
  own filesystem, so `downloads/` and the library must be directories of **one** dataset
  (`<pool>/media`), not sibling or child datasets (inference from [TR1] and ZFS datasets being
  separate mounts).
- Inside the containers, mount the dataset's root once (`/data`), as the repo already does
  with `${MEDIA_PATH}:/data`, so the *arr see one filesystem.
- SQLite databases (the *arr and Plex config) do not belong on a network or shared
  filesystem, because locking is unreliable there [SQ1]. They stay on each VM's local disk.

### Option M1: virtiofs (Proxmox built-in)

- Shipped in Proxmox VE 8.4 (2025-04-09) as directory passthrough [P3]. Configured as a
  cluster directory mapping, then `virtiofs<N>: dirid=...` on the VM. Options: `cache`
  (auto default, always, metadata, never), `direct-io`, `expose-xattr`, `expose-acl`. The
  guest mounts it as `mount -t virtiofs <dirid> <mountpoint>` or through fstab. Needs
  `apt install virtiofsd` on the host and guest kernel 5.4 or newer [P1].
- Proxmox starts virtiofsd with `--announce-submounts` always and `--syslog`, and with
  `--inode-file-handles=prefer` only for Windows guests [P6]. Submount announcement reports a
  different device number for each mount inside the share, which prevents inode collisions
  and makes `syncfs` reach every submount [V1]. A child dataset inside the share is
  therefore seen as a separate filesystem by the guest, so hardlinks to it fail as they
  would on the host (inference).
- `link()` is passed through to the host filesystem, so hardlinks inside one dataset work
  the same as on the host (inference: virtiofs is FUSE passthrough "with similar
  performance and semantics as the source filesystem" [P1]).
- **Limits on Proxmox VE 9.3** (docs and code):
  - "Memory related features such as live migration, snapshots, and hibernate are not
    available with virtiofs devices" [P1]. In the code, the check blocks only operations that
    save VM state: `Cannot live-migrate, snapshot (with RAM), or hibernate a VM with:
    virtiofs` [P6]. Disk-only snapshots and vzdump backups are not blocked (inference from
    the same function being the snapshot blocker check).
  - Memory hotplug is refused with virtiofs (`Memory hotplug does not work in combination
    with virtio-fs`). The VM's RAM moves to a shared `memory-backend-memfd` [P6].
  - If virtiofsd crashes or stops responding, the mount hangs in the guest until the VM is
    fully stopped [P1].
  - No read-only option in Proxmox's `virtiofs` schema [P6]. virtiofsd itself has
    `--readonly`, but Proxmox does not pass it. Its FAQ's alternative is to share a read-only
    bind mount [V1]: a host-side `mount -o bind,ro` of the dataset used as the GPU VM's mapping
    path. Otherwise `ro` in the guest's fstab is guest-enforced only.
  - The Proxmox roadmap lists "Lift current restrictions on virtiofs-enabled VMs (live
    migration, snapshots with RAM, hibernation)" as future work [P2]. Upstream virtiofsd
    already supports migration with QEMU 8.2+ [V1]. Latest upstream release as of 2026-11-26: virtiofsd 1.15.0
    (2026-11-20) [V2].
- Two guests on one share: `cache=auto` caches metadata and lookups for a short timeout (1 s)
  and data only while a file is open; `cache=never` (called `none` in the article) caches
  nothing; `cache=always` never expires and can serve stale data when another party writes
  [X2]. For the read-only GPU VM, `auto` or `never` fit; `always` does not (inference).
- On a single node, losing live migration costs nothing. The GPU VM, which holds a
  passed-through device, can't live-migrate anyway (inference). What matters is the
  snapshot-with-RAM loss on both VMs.
- UID/GID pass through unchanged (Proxmox sets no `--translate-uid` [P6]), so the guests' PUID/PGID
  must match the owner on the host dataset.
- The shared dataset is not a VM disk, so it is outside vzdump. It is backed up with the
  host's ZFS snapshots and replication (inference).

### Option M2: NFS from the host

The host runs the kernel NFS server and exports `<pool>/media`, either through ZFS's
`sharenfs` property or `/etc/exports` [Z1]. The Media VM mounts it read-write, and the GPU VM
mounts it with an export that is read-only on the server side.
- Hardlinks: `link()` works within one exported filesystem. A child dataset would need its
  own export or `crossmnt`, and links still cannot cross it (inference).
- For: no restriction on VM snapshots with RAM, migration or memory hotplug. The read-only
  export is enforced by the server. A well-known, mature stack.
- Against: one more daemon on the Hypervisor Host and exports on a network. Bind them to the
  host-only bridge or restrict them by client address (inference). The guest must mount before
  Docker starts, otherwise containers bind an empty directory (inference: systemd mount
  ordering, `RequiresMountsFor` on `docker.service`). With the default hard mount, a stuck
  server hangs I/O much like a dead virtiofsd (inference). Traffic goes through the virtio NIC
  and the host's network stack. That is slower per operation than virtiofs, but it is not
  capped by the 1G switch (inference).

### Effect on Plex (both options)

Plex's "Update my library automatically" relies on OS change notifications and "will
generally not work for network shares mounted via SMB, NFS, AFP, or similar" [X1]. Writes by
the Media VM reach the GPU VM through the host, not through the GPU VM's kernel, so its
inotify does not fire (inference; this applies to virtiofs too). Workarounds: periodic scans
(15 min minimum interval) [X1], or the Sonarr/Radarr "Plex Media Server" connection, which
asks Plex to update the library on each import (`OnDownload`, `UpdateLibrary`) [SR1].

### Other combinations (not recommended by the sources above, listed for completeness)

- SMB from the Samba LXC that ADR 0001 allows: adds a third sharing protocol, and SMB
  hardlink support depends on protocol extensions (not evaluated here).
- Moving Plex into the Media VM or the *arr into the GPU VM removes the share entirely, but
  contradicts ADR 0001's placement criteria (GPU ownership vs torrent traffic).

- virtiofs together with VFIO passthrough in the GPU VM: the memfd shared memory backend

  combination.
- That vzdump backups and disk-only snapshots of a virtiofs VM run cleanly on 9.3 (the code
