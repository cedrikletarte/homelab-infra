# Research: backup tools and targets for the new server

Ticket: "Outils et cibles de sauvegarde". Researched 2026-11-26.

Question: which tools and targets give a 3-2-1 backup of the critical data (Immich, Vaultwarden, n8n, Postgres, GitLab, Nextcloud AIO) without stopping every stack each week? Covers restic and its wrappers, Borg/borgmatic, Kopia, ZFS snapshots with sanoid/syncoid, how to get consistent database copies, off-site targets with current prices, the local target (old server or external disk), encryption, retention, restore checks and notifications.

This document lays out facts and trade-offs. It does not make the decision.

## 1. Starting point: what the current script does

From `scripts/docker-backup/README.md` and `docker_backup.sh`:

- Every Sunday at 03:00 (cron set up by the Ansible `maintenance` role), it stops the Nextcloud AIO containers through AIO's `daily-backup.sh`, then runs `docker compose down` on every running stack under `stacks/` and `infrastructure/`.
- It writes one full `tar.gz` per source: the whole Docker volumes directory, the Immich data directory and the Nextcloud data directory. Each run is a full copy, with no deduplication or incremental step.
- It restarts the stacks it stopped, then uploads the repository directory and the archives to OneDrive through an `rclone crypt` remote (XSalsa20-Poly1305, encrypted names).
- It keeps the last 7 dated folders on OneDrive. That is about 7 weeks of history, all of them full copies.
- It notifies Discord through an n8n webhook, and writes a success marker that `docker_pull_and_run.sh` checks before it updates images.

Gaps compared with a 3-2-1 setup:

- Only one backup copy exists, and it is off-site. There is no local backup copy for a fast restore.
- Downtime grows with the data, because all stacks stay stopped for the whole `tar` run.
- Every run uploads the full data again.
- Nothing checks that a backup can actually be restored.
- The notification depends on n8n, one of the services being backed up, which is down during the backup window.

The success marker and the "no update without a fresh backup" rule are worth keeping whatever tool is chosen.

## 2. How to get consistent data without long downtime, per application

The general rule: databases get a logical dump or an atomic snapshot, and files are backed up *after* the dump. A plain file copy of a running database is not safe.

### PostgreSQL (shared instance, used by n8n among others)

- `pg_dump` "makes consistent exports even if the database is being used concurrently" and "does not block other users accessing the database (readers or writers)". Roles and other global objects need `pg_dumpall` (`pg_dumpall --globals-only`) ([PostgreSQL 19 docs, pg_dump](https://www.postgresql.org/docs/current/app-pgdump.html)).
- A filesystem snapshot of a running server also works, if the snapshot is atomic and includes the WAL. On restore, PostgreSQL treats it as a crash and replays the WAL. Running `CHECKPOINT` first shortens that recovery. If data and WAL sit on different filesystems, the snapshots "must be simultaneous" ([PostgreSQL 19 docs, file system level backup](https://www.postgresql.org/docs/current/backup-file.html)).
- Conclusion: no PostgreSQL container ever needs to be stopped for a backup.

### Immich (its own Postgres with VectorChord, plus the upload location)

From the official docs ([Immich backup and restore](https://docs.immich.app/administration/backup-and-restore)):

- Immich writes its own database dumps to `UPLOAD_LOCATION/backups`: daily at 02:00 by default, keeping the last 14. Both settings are under Administration > Settings > Database Dump Settings. The dumps hold metadata only, not photos.
- Only `library`, `upload` and `profile` are critical. `thumbs` and `encoded-video` can be regenerated by re-running jobs, but the docs still recommend backing up all of `UPLOAD_LOCATION`.
- Stopping `immich-server` is described as "the best way", but it is not required. "If stopping isn't an option, back up the database first and the filesystem second." With that order, the worst case after a restore is files the database doesn't know about. The reverse order leaves assets that point to missing files.
- Restore works from the UI (Administration > Maintenance, with an automatic restore point and rollback) or on a fresh install. The backup and restore process changed in v2.5.0. The stack in this repo runs v3.4.2.
- The docs recommend a 3-2-1 strategy and say "You still need to take care of using an actual backup tool".
- Conclusion: schedule the file backup after the 02:00 dump and back up `UPLOAD_LOCATION`, dumps included. No stop needed. Excluding `thumbs`/`encoded-video` from the off-site copy is a size-versus-restore-time trade-off.

### Vaultwarden (SQLite in a named volume in this repo)

From the [Vaultwarden wiki, Backing up your vault](https://github.com/dani-garcia/vaultwarden/wiki/Backing-up-your-vault):

| Item | Priority |
|---|---|
| `db.sqlite3` | Required |
| `attachments/` | Required |
| `config.json` | Recommended. Holds plaintext secrets such as the admin token, so encrypt it. |
| `rsa_key*` | Recommended. Losing them logs everyone out. |
| `sends/` | Optional |
| `icon_cache/` | Optional |

- The live database should be copied with SQLite's online backup API. Since 1.32.1 it is built in: `docker exec <container> /vaultwarden backup`. The image in this repo is 1.37.5, so it has it. `sqlite3 .backup` and `VACUUM INTO` are the alternatives. A raw file copy is only safe when the database is not in use, and it must include the `-wal` file.
- On restore: stop the container and delete any stale `db.sqlite3-wal` before you drop in a `.backup` copy.
- The wiki warns against relying *only* on filesystem or VM snapshots, because recovering from them can be awkward.
- Conclusion: run `/vaultwarden backup` before each run and back up the data directory. No stop needed.

### n8n (data in the shared Postgres plus the `.n8n` volume)

- A full backup is the database plus the `.n8n` folder, because credentials are encrypted with the key stored there (`config` file or `N8N_ENCRYPTION_KEY`). Without the key, credentials cannot be recovered. CLI exports (`--backup`) do not include the key ([n8n docs, backup and restore](https://docs.n8n.io/deploy/host-n8n/keep-n8n-running/backup-and-restore)).
- Conclusion: a `pg_dump` of the n8n database plus the `n8n_data` volume. Also keep the encryption key separately with the other backup secrets.

### GitLab EE (Omnibus container with bundled Postgres)

From the [GitLab docs, back up GitLab](https://docs.gitlab.com/administration/backup_restore/backup_gitlab/):

- `docker exec -t <container> gitlab-backup create` runs while GitLab is up. It covers the database, repositories, LFS, uploads, CI artifacts and logs, the package and container registry, wikis, Pages, Terraform state and snippets.
- It does **not** cover the configuration. `gitlab.rb` and, most importantly, `gitlab-secrets.json` (the config volume in Docker) must be backed up separately, along with SSH host keys and TLS material. Redis is not covered either.
- For full consistency there should be "no pending or running background jobs". The default `tar` streaming can fail with "file changed as we read it". `STRATEGY=copy` avoids that, at the cost of up to 1x extra disk space. Only repositories can be backed up incrementally (`INCREMENTAL=yes`).
- `backup_keep_time` prunes local archives only.
- A filesystem snapshot (the docs' example uses LVM) requires `gitlab-ctl stop` first. Gitaly Cluster does not support snapshot backups. This repo does not use Gitaly Cluster.
- Conclusion: run `gitlab-backup create STRATEGY=copy` online into a local directory, keep only one or two archives locally, and let the backup tool deduplicate them. Back up the config volume every time. One caveat: `gitlab-backup` writes a new tar each time, so deduplication works well only if the archive is not compressed differently on each run. That is worth testing with the chosen tool before relying on it.

### Nextcloud AIO

From the [AIO README](https://github.com/nextcloud/all-in-one) (Backup section and FAQ):

- AIO has a built-in BorgBackup solution: "incremental, differential, compressed and encrypted". It is managed from the AIO interface (create, restore, integrity check and repair) and can be scheduled daily or weekly. It covers the database, the data directory and the mastercontainer configuration. It does *not* cover external-storage mounts or `NEXTCLOUD_MOUNT` paths.
- The default retention is `--keep-within=7d --keep-weekly=4 --keep-monthly=6`, adjustable with `BORG_RETENTION_POLICY`.
- It can back up straight to a remote borg repository over SSH. That supports append-only keys "to counter ransomware". `BORG_APPEND_ONLY=true` skips prune/compact, which then have to run on the server.
- A local AIO borg repository can be synced off-site with rsync or rclone. The README gives a script that first creates an `aio-lockfile` and checks for `lock.roster`, so the repository is never copied mid-write.
- AIO's backup still stops the Nextcloud containers (`DAILY_BACKUP=1` "will automatically stop the containers and create a backup"). Because borg is incremental, the downtime is that of an incremental run, not a full tar. `CHECK_BACKUP=1` runs the integrity check without stopping anything.
- Using your own tool instead is "disrecommended". AIO says it is supported only if the containers are shut down properly first, which is what the current script already does.
- Excluding the data directory (`.noaiobackup`) risks the database and files getting out of sync.
- Conclusion: there are two realistic paths. (a) Use AIO's built-in borg, with a nightly or weekly short stop handled by AIO, pointed at a local or LAN borg repository and synced off-site. (b) Keep stopping AIO with the script, but take an atomic filesystem snapshot, restart immediately and back up from the snapshot, so the downtime is seconds. Path (b) relies on a supported stop/start plus an unofficial snapshot step.

### Summary: is weekly downtime still needed?

| App | Stop needed? | Method |
|---|---|---|
| Shared Postgres / n8n | No | `pg_dump`/`pg_dumpall`, plus the `.n8n` volume |
| Immich | No | Built-in dump at 02:00, then files (DB first) |
| Vaultwarden | No | `/vaultwarden backup`, then the data directory |
| GitLab | No | `gitlab-backup create STRATEGY=copy` plus the config volume |
| Nextcloud AIO | Short stop | AIO borg (incremental) or stop, snapshot, start |
| Everything else (Homarr, Portainer, \*arr configs, Grafana...) | No for a crash-consistent copy | Volume backup; most use SQLite, so a snapshot or a brief per-stack stop is safer |

## 3. Backup tools

Versions were checked against each project's GitHub releases feed on 2026-11-26.

### restic (0.20.0, 2026-11-19)

- Single Go binary, encrypted (repository password), deduplicated, compressed (zstd since repository v2; `fastest`/`better` levels added in 0.19.0) ([restic changelog](https://github.com/restic/restic/blob/master/CHANGELOG.md)).
- Backends: local, SFTP, REST server, S3-compatible (B2, Wasabi, IDrive e2), native B2, Azure, GCS, Swift and **any rclone remote**, which covers OneDrive. 0.18 improved retries for flaky rclone backends, and 0.20.0 adds support for B2 multi-bucket application keys ([changelog](https://github.com/restic/restic/blob/master/CHANGELOG.md)).
- Database dumps: `restic backup --stdin-from-command -- <dump command>` stores the dump without a temporary file. If the command exits non-zero, no snapshot is created. Piping with `--stdin` can silently store an empty dump, so the docs warn against it ([restic docs, backup](https://restic.readthedocs.io/en/stable/040_backup.html)).
- Verification: `restic check --read-data-subset=n/t` (rotating subsets), `x%` or a size ([restic docs, working with repos](https://restic.readthedocs.io/en/stable/045_working_with_repos.html)).
- Copies between repositories: `restic copy` deduplicates correctly only if the target was created with `init --copy-chunker-params` ([same page](https://restic.readthedocs.io/en/stable/045_working_with_repos.html)). This matters for a "local repo, then copy off-site" design.
- Retention: `forget --keep-daily/--keep-weekly/--keep-monthly`, then `prune` (or `forget --prune`). Prune locks the repository, and `forget`/`prune` need delete access ([restic docs, forget](https://restic.readthedocs.io/en/stable/060_forget.html)).
- Ransomware protection: **rest-server** (0.15.0, 2026-11-23) with `--append-only` "prevents deletion and modification of existing backups". With `--private-repos`, each user is limited to its own repository ([rest-server README](https://github.com/restic/rest-server)). Pruning then has to run from another machine or key.
- restic has no native S3 Object Lock handling.
- Weakness: restic is a CLI only. Scheduling, hooks, notifications and retention need a wrapper.

|---|---|---|---|

| **resticprofile** | v0.35.0 (2026-11) | Declarative profiles (TOML/YAML/JSON) with inheritance and groups; generates systemd/cron schedules; retention and check after backup; run-before/after and on-error commands; HTTP hooks before, after success and after failure; Prometheus file or pushgateway output; stdin backups; auto-init of a secondary repository with `copy-chunker-params` ([README](https://github.com/creativeprojects/resticprofile)) | Fits the Ansible, config-in-git model; no UI |
| **autorestic** | v1.8.3 (2024-08) | YAML config, multiple backends, hooks, Docker volume backup ([README](https://github.com/cupcakearmy/autorestic)) | No release in over two years, so there is a maintenance risk |

### BorgBackup (stable 1.4.5, 2026-07; 2.0 still in beta, 2.0.0b25) and borgmatic (2.2.0, 2026-10)

- Borg 1.4 is mature, deduplicated, compressed and encrypted, but it needs SSH access to a host running `borg serve` (or a local path). Hetzner Storage Box and BorgBase provide that. Borg 1.4 cannot write directly to B2, S3 or OneDrive.
- Borg 2 adds `rclone:`, `s3:`, `b2:` and `sftp:` repository URLs ([borg master docs, repository URLs](https://borgbackup.readthedocs.io/en/master/usage/general.html)). It is still a beta (2.0.0b25 is the latest release in the [releases feed](https://github.com/borgbackup/borg/releases)), and its repositories are not compatible with 1.x.
- Nextcloud AIO already ships borg. Using borg elsewhere means one tool family for everything.
- **borgmatic** is the wrapper ([docs](https://torsion.org/borgmatic/)):
  - Database hooks for PostgreSQL, MariaDB/MySQL, SQLite, MongoDB and others stream dumps directly into Borg with no temporary file. A database in a container can be reached with `container:` (since 2.0.8) or by overriding the dump command with `docker exec`. `borgmatic restore` exists, but it is destructive and does not create the target database ([database docs](https://torsion.org/borgmatic/how-to/backup-your-databases/)).
  - Filesystem snapshot hooks for ZFS (since 1.9.3), Btrfs and LVM (since 1.9.4). The datasets are listed in `source_directories` and a `zfs:` line turns it on ([snapshot docs](https://torsion.org/borgmatic/how-to/snapshot-your-filesystems/)).
  - Checks: `repository`, `archives`, `data` (decrypts everything), `extract` (dry-run extract of the latest archive) and `spot`, which "compares file counts and contents between your source files and the latest archive". Each has a configurable `frequency` ([consistency checks](https://torsion.org/borgmatic/reference/configuration/consistency-checks/)).
  - Monitoring: Healthchecks, ntfy, Apprise, Uptime Kuma, Cronitor, PagerDuty, Pushover, Sentry, Loki, Zabbix ([monitoring docs](https://torsion.org/borgmatic/how-to/monitor-your-backups/)).
- Weakness: off-site is limited to borg-over-SSH hosts until Borg 2 is stable. Moving from Borg 1 to Borg 2 later means a repository migration.

### Kopia (0.23.1, 2026-06)

- Encrypted (AES-256 or ChaCha20), compressed (pgzip/s2/zstd), with optional Reed-Solomon error correction. Policies at global, host and path level control schedule and retention. It has a CLI, KopiaUI and a server mode. Backends: S3-compatible, B2, Azure, GCS, WebDAV, SFTP, rclone (experimental) and Kopia server ([Kopia features](https://kopia.io/docs/features/)).
- Notifications are built in: email, Pushover and webhook notification profiles ([CLI reference](https://kopia.io/docs/reference/command-line/common/)).
- Ransomware protection: S3 Object Lock in COMPLIANCE mode with `--retention-mode`/`--retention-period` and lock extension during maintenance. It works on S3 and S3-compatible storage (B2 through its S3 API, not the native B2 engine), Azure and GCS ([Kopia ransomware protection](https://kopia.io/docs/advanced/ransomware-protection/)). This is the most complete immutability story of the three tools.
- Weakness: still 0.x. rclone (and so OneDrive) support is marked experimental. It has no built-in database dump hooks, only generic before/after actions.

### ZFS snapshots with sanoid/syncoid (sanoid 2.3.0, 2025-06)

Relevant only if the new server's 4x 8 TB pool is ZFS. That is decided in another ticket.

- **sanoid**: policy-driven snapshot creation and pruning from a TOML file, run from a one-minute cron. It also has pre/post snapshot scripts and Nagios-style monitoring of snapshots, pool health and capacity ([sanoid README](https://github.com/jimsalterjrs/sanoid)).
- **syncoid**: incremental `zfs send/receive` over SSH. It is recursive and resumable, uses mbuffer/lzop when available, and supports `--sendoptions` (for example raw sends of encrypted datasets, which an untrusted target can store without the key) ([README](https://github.com/jimsalterjrs/sanoid), [syncoid source](https://github.com/jimsalterjrs/sanoid/blob/master/syncoid)).
- Atomicity: "Snapshots are created atomically", and `-r` snapshots "are all created at the same time" ([zfs-snapshot(8)](https://openzfs.github.io/openzfs-docs/man/master/8/zfs-snapshot.8.html)). One `zfs snapshot -r` across the app datasets gives a crash-consistent point in time for every database and its files together. PostgreSQL documents this as safe ([backup-file](https://www.postgresql.org/docs/current/backup-file.html)).
- That gives a pattern with almost no downtime: stop AIO (and, if wanted, the SQLite-based apps), take the snapshot, restart (seconds), then let restic, borg or kopia read from the snapshot at leisure. borgmatic automates the snapshot part.
- Limits:
  - A snapshot on the same pool is not a backup.
  - `zfs send` needs a ZFS receiver: the old server with disks, or a provider that offers ZFS targets. Object storage and OneDrive cannot receive it.
  - Native ZFS encryption combined with send/receive has a history of bugs. The long-running corruption issue [openzfs#12014](https://github.com/openzfs/zfs/issues/12014) was closed in 2025. A maintainer said it "affected only non-raw sends" and was fixed. Test with the OpenZFS version that ships with the chosen OS.
  - The Vaultwarden wiki cautions against relying only on snapshots ([wiki](https://github.com/dani-garcia/vaultwarden/wiki/Backing-up-your-vault)).

### Tool comparison

| | restic + wrapper | borg 1.4 + borgmatic | Kopia | sanoid/syncoid |
|---|---|---|---|---|
| Maturity | 0.x but long-lived, very active | 1.x stable, Borg 2 beta | 0.x, active | Stable, slow release cadence |
| Off-site backends | Everything, including OneDrive via rclone | SSH/borg hosts only | S3/B2/Azure/GCS/SFTP; rclone experimental | ZFS receivers only |
| DB dump integration | `--stdin-from-command` or wrapper hooks | Native hooks, streamed | Generic actions | None (atomic snapshot instead) |
| Filesystem snapshot integration | Wrapper hooks (scripts) | Native ZFS/Btrfs/LVM | Actions | Native |
| Immutability | rest-server append-only | Append-only SSH keys | S3 Object Lock | Raw send to a separate host |
| Restore checks | `check --read-data-subset` | `check` incl. `spot`/`extract` | `snapshot verify` and maintenance | `zfs scrub` on the target |
| Notifications | Backrest/resticprofile hooks (Discord, Healthchecks) | Many monitoring hooks | Email/Pushover/webhook | Monitoring flags for Nagios |
| Fits AIO | Separate tool next to AIO's borg | Same family as AIO's borg | Separate | Complements any of them |

## 5. Local target: the old server or an external disk

The old server (i5-2400, 16 GB RAM, no disks after the move) would need disks bought for it. Possible roles:

- **restic rest-server in `--append-only` mode.** The main server can add backups but cannot delete them. Prune runs on the old server with a separate key ([rest-server](https://github.com/restic/rest-server)).
- **borg over SSH** with an append-only key. AIO can back up to it directly ([AIO remote borg](https://github.com/nextcloud/all-in-one#are-remote-borg-backups-supported)).
- **ZFS receive target for syncoid**, if the main server uses ZFS. This needs ZFS on the old server too. 16 GB is enough for a receive-only pool.
- Because it is a separate machine, a compromised or broken main server cannot reach it (in append-only mode), unlike a disk that stays mounted.
- Downsides:
  - It sits in the same house, so it adds a second copy and a second medium but not a second site.
  - It draws power all the time, unless woken on a schedule with Wake-on-LAN.
  - It is one more machine to patch, which goes against the low-maintenance principle.

An **external USB disk** on the main server is simpler: AIO's own example rsyncs its borg repository to a drive listed in fstab, mounted only during the run ([AIO README](https://github.com/nextcloud/all-in-one#sync-local-backups-regularly-to-another-drive)). But it is not protected from the host's own root user unless it is unmounted or rotated, and it needs physical handling.

An internal-only option (a backup dataset on the same IronWolf pool, or on the 870 SSD) is fast to restore, but it shares the machine and power supply. It counts as a "copy", not a separate device.

## 6. Cross-cutting concerns

- **Encryption and keys.**
  - All three tools encrypt client-side with a password or key: restic and Kopia always; borg, AIO's borg and rclone crypt when configured to.
  - The trap is circular: if the repository passwords live only in Vaultwarden, and Vaultwarden is in the backup, a total loss is unrecoverable.
  - The current README already warns about this for rclone crypt. The same applies to the AIO borg key, `gitlab-secrets.json`, the n8n encryption key and any restic or Kopia passwords.
  - They need a copy outside the server: paper, a second password manager, or a trusted family member.
- **Retention.** AIO's default (`7d / 4 weekly / 6 monthly`) is a reasonable reference. restic `forget` and borgmatic `keep_*` express the same thing. Wasabi's 90-day minimum makes frequent pruning there pointless. Append-only targets need pruning from a separate, more trusted place.
- **Restore checks.** None of the tools proves that an *application* can be restored. Levels to consider:
  1. Repository integrity: `restic check --read-data-subset`, borgmatic `repository/archives/data`, Kopia verify and maintenance.
  2. File-level checks: borgmatic `spot`/`extract`, or restoring a sample.
  3. A periodic application restore. For example, restore the Immich dump into a throwaway Postgres container, open the Vaultwarden SQLite copy with `PRAGMA integrity_check`, restore a GitLab backup into a test container, or restore AIO into a test instance. This is the only level that catches missing secrets such as `gitlab-secrets.json` or the n8n key.
- **Notifications.**
  - Today the alert goes through n8n, which is itself backed up and stopped during the window.
  - A "dead man's switch" catches the case where the job never runs: Healthchecks (BSD-licensed, self-hostable, has a Discord integration; the hosted free plan covers 20 jobs, see [README](https://github.com/healthchecks/healthchecks) and [pricing](https://healthchecks.io/pricing/)), BorgBase's stale-repo alerts, or a Prometheus alert on a resticprofile or rest-server metric. Prometheus and Grafana are already in the stack.
  - Backrest and borgmatic both speak to Healthchecks. Backrest also speaks to Discord directly.

## 7. Implications for the decision

Combinations that stand out, with no ranking implied:

1. **restic everywhere (resticprofile or Backrest) + local rest-server + B2 Toronto or Hetzner.**
   - One tool for all stacks, with dumps through `--stdin-from-command` or pre-hooks, and pre-hooks for `/vaultwarden backup` and `gitlab-backup`.
   - The local copy goes to an append-only rest-server on the old server. The off-site copy is either `restic copy` to B2 Toronto (data stays in Canada, no minimums) or SFTP to a Hetzner box (cheapest per TB).
   - Nextcloud stays on AIO's built-in borg, pointed at the old server or a disk, with its repository synced off-site using the lockfile procedure. Alternatively, AIO is snapshotted and read by restic.
   - resticprofile fits the "config in git, deployed by Ansible" principle. Backrest fits "dedicated tool with a UI".
   - OneDrive can stay as a transitional third copy through the rclone backend, within its 1 to 2 TB cap.
2. **borg everywhere (borgmatic) + Hetzner Storage Box or BorgBase.**
   - Same tool family as AIO.
   - Native, streamed database hooks; native ZFS/LVM snapshot hooks; the richest checks (`spot`) and monitoring hooks.
   - Off-site is limited to borg-over-SSH hosts. B2 and OneDrive are out until Borg 2 is stable, and Borg 2 will mean a repository migration later.
3. **ZFS-centric: sanoid locally + syncoid to the old server + restic, borg or kopia off-site from snapshots.**
   - Gives near-zero downtime for every stack, Nextcloud AIO included (stop, snapshot, start in seconds), and fast local rollback.
   - Depends on the new server's pool being ZFS, and on the old server also running ZFS.
   - Adds the operational weight of two ZFS hosts.
4. **Kopia + B2 (S3 API) with Object Lock.** The strongest protection against ransomware or a compromised host for the off-site copy. The downsides are the 0.x status and the lack of database hooks, and it is a separate tool next to AIO's borg.

Questions the owner needs to settle:

- **Data sizes.** How large are the Immich originals, the Nextcloud data and GitLab today, and what growth is expected over two to three years? This decides whether OneDrive's 1 to 2 TB cap and the Hetzner 1 TB vs 5 TB tier are relevant.
- **Upload bandwidth** of the Bell connection, which sets how long the first off-site seed takes.
- **Storage location.** Must off-site data stay in Canada (B2 Toronto), or are EU (Hetzner, Finland or Germany) and US locations acceptable?
- **The old server.** Is it worth buying disks and running it all the time as the local append-only or ZFS target, or is an external disk enough?
- **ZFS.** Will the new data pool be ZFS? If so, snapshots become the consistency mechanism and syncoid an option.
- **Nextcloud AIO.** Keep AIO's built-in borg (official, short stop handled by AIO) or replace it with the general tool plus stop, snapshot, start (one tool, but outside AIO's supported path)?
- **OneDrive.** Keep it as an extra copy during the transition, or drop it?
- **Restore drills.** How often, and how deep (repository check only, or a real application restore)?
- **Backup secrets.** Where do the key and password copies live outside the server, and who else in the family can reach them?
- **Alerting.** Should it stay on n8n and Discord, or should a dead man's switch (Healthchecks, self-hosted or hosted) or Prometheus alerting be added so a missed run is detected?
